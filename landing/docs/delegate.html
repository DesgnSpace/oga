Docs / Hand off work

Hand off your first piece of work

You don't fill in a form. You ask the coding agent you already use, in plain language, and it sets the work up for you.

Ask for it in plain language

Once your agent is connected, ask for the work the way you'd ask a colleague:

"Send the failing test suite off to a fast model."

"Have someone else write the changelog while I keep going on the API."

Your agent writes the brief, names the folder the work happens in, and either lets Oga choose the account and model or names one itself. The brief goes out as written, at whatever length the job needs — a sentence for a small job, more when there is more to say. You get an ID back as soon as the work starts. From there it runs on its own account, unattended.

Or straight from your shell

When you already know what you want done, you don't need to go through an agent. oga delegate starts the work and hands you its ID:

oga delegate "Port the CSV importer to the new parser and keep its tests green."

It runs in the folder you're standing in, on the account and model Oga picks. Name one yourself with --worker and --model, give it its own branch with --worktree, or point it at another folder with --cwd. Already know what kind of work this is? Say so with --kind, so a loved model for that kind isn't missed. Want a say in how hard the model thinks? Set --effort directly.

Pass - to take the brief from standard input, for when you've already written it down:

oga delegate - < brief.md

What's worth handing off

Handing off costs you a brief and a wait. It pays for itself on work with its own finish line — build this screen, port this module, review this branch, research this question. It doesn't pay for a rename, a typo, or a one-line change: by the time you've described those, you could have done them.

The same goes for anything you're standing over. Work you'd interrupt every two minutes belongs in your own session.

What it's allowed to touch

Every piece of work carries the area you approved: what it may read, and what it may change. Reading the whole folder and writing to one part of it is the usual shape.

  • Naming a folder covers everything inside it.
  • ** means the whole folder you're working in.
  • A path that doesn't exist yet means only itself. If the work will create files under a new folder, write out/**, not out.

Approving an area once is enough — later work in the same project reuses it without asking again. The area is a permission, not a reading list; which files actually get opened is up to whoever does the work.

What it works with

Whoever does the work gets the tools you already connected for that project, alongside Oga's own. A database, a browser, an issue tracker — if your coding agent can reach it in that folder, so can the work you hand off.

Work stays where you send it: it can report back and ask, but it can't hand the job on to someone else. When a piece of work is big enough to need help, say so as you send it — ask your agent to let it hand work onward, and it gets to split the job up itself.

Who ends up doing it

Name nothing, and the work uses your default model when you set one. Otherwise Oga chooses from the workers and models you turned on. Name a worker and model when the work needs a specific destination.

Naming a model, you can use the short name Settings shows instead of typing it in full, as long as it names only one model on that worker. A short name that could mean more than one is refused, listing the models it could mean, and a model you haven't switched on in Settings is always refused, however you asked for it.

Workers arrive with default habits — clearing small holdups themselves, looking code up before searching blindly, and ending branch work in a pull request. The lookup understands Rust, Python, Go, PHP, Ruby, Java, Swift, C#, C, and C++ source. Those defaults live in Settings as a worker prompt you own top to bottom: reorder it, rewrite it, or delete it, and nothing is added behind your back.
